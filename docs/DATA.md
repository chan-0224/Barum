## 1. 성분 DB (핵심)

**식약처 화장품 원료성분정보 21,863건 → Supabase `ingredients` 적재 완료.**

### 이 DB는 '화장품 표준명' 체계를 쓴다

구어체로 조회하면 0건이 나온다. 데이터 결함이 아니라 대한화장품협회 표준명 체계를 따르는 것이고, **전성분표도 법적으로 이 표준명을 쓴다.**

| 구어체 | 결과 | 표준명 | 결과 |
|---|---|---|---|
| 히알루론산 | 0건 | 하이알루로닉애씨드 | 50건 |
| 아스코르빈산 | 0건 | 아스코빅애씨드 | 10건 |
| 디메치콘 | 0건 | 다이메티콘 | 470건 |

**따라서 OCR이 읽은 문자열과 DB 키가 일치한다 → 완전일치 매칭이 주 경로로 성립.** 별도 매핑 레이어 불필요.

확인된 표준명: `하이알루로닉애씨드` `소듐하이알루로네이트` `레티놀` `나이아신아마이드` `아데노신` `판테놀` `살리실릭애씨드` `아스코빅애씨드` `다이메티콘` `글리세린` `정제수` `부틸렌글라이콜`

### 필드 채움률

| 필드 | 채움률 |
|---|---|
| `INGR_KOR_NAME` 표준명 | 100% (21,863) |
| `ORIGIN_MAJOR_KOR_NAME` 기원·정의 | 99.7% |
| `INGR_ENG_NAME` 영문명 | 94.2% |
| `INGR_SYNONYM` 이명 | 16.5% |
| `CAS_NO` | 7.2% |

이명 채움률이 낮지만 문제되지 않는다. 이명은 `다이메틸 ↔ 디메칠` 같은 표기 변형이라 OCR 오독 보정용 보조 인덱스로만 쓴다.

표준명은 21,863건 전부 고유 → UNIQUE 키(upsert 기준). 최대 길이 528자라 `text`.

### 성분 조합 궁합 정보는 공공데이터에 없다

'사용제한 원료'(31,191건)는 국가별 배합 금지·배합 한도일 뿐 조합 금기가 아니다. 규제 대상이 아니므로 어떤 공개 API에도 없다.
→ **룰테이블 수기 구축이 유일한 방법.** 피부과 문헌·브랜드 공식 가이드 기반, 각 룰에 출처 명시.

### 폐기

`식약처 화장품 관련 정보(15020628)`는 제조판매업체 등록 현황이라 제품 DB로 쓸 수 없다. 제품 카탈로그는 별도 수집(왕종휘).

## 2. 날씨 (`daily_context.py`)

```python
get_daily_context(lat, lon) -> {"temp", "humidity", "pm10", "pm25"}
```

실측 1.2초. 기상청·에어코리아 병렬 호출(`asyncio.gather`), 한쪽이 죽어도 나머지는 반환.

**기상청 단기예보 (15084084)**
- 위경도가 아니라 격자좌표(nx, ny). Lambert Conformal Conic 변환 구현 완료
- 검증: 서울시청 (60,127) / 부산시청 (98,76) / 제주시청 (53,38) / 대전시청 (67,100) — 공식값 일치
- `base_time` 02·05·08·11·14·17·20·23시 발표, +10분 후 제공 → 45분 여유 두고 직전 슬롯 선택
- 사용 필드: `TMP`(기온) `REH`(습도)

**에어코리아 (15073861)**
- 서비스명은 `ArpltnInforInqireSvc` (`ArpltnInqirySvc`로 쓰면 코드 12 에러)
- 첫 응답이 20초를 넘긴 적 있음 → 타임아웃 40초
- 고장 측정소는 값이 `"-"`, 플래그 `"통신장애"` → 필터링 필수
- `ver=1.0`에도 `pm25Value` 포함
- 개발계정 트래픽 500 → 캐싱 필수

**시도 자동 판정**: 광역시도 17개 중심좌표 최근접. API 호출 0.
한계 — 경계 폴리곤이 아닌 중심점 기준이라 경기 남부가 서울로 붙는다. 미세먼지가 시도 평균값이라 수치 차이는 작다.

**캐싱**: 캐시 키에 시간 버킷 포함 → TTL 로직 없이 기상청은 발표시각당 1콜, 에어코리아는 시간당 1콜.

**UV(자외선지수)는 명시적 제외.** 별도 API가 필요한데 사실상 상수라 장애 지점만 늘어난다. 반환값에 키 자체를 두지 않는다.

## 3. 인증키 (data.go.kr)

- 5종 전부 **Decoding 키 하나로 공용**
- httpx·requests는 파라미터를 자동 인코딩하므로 반드시 Decoding 키. Encoding 키를 넣으면 `%`가 이중 인코딩되어 실패
- 발급 직후 ~1시간은 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 발생 가능(정상)
- `raise_for_status()`가 에러 메시지에 URL을 통째로 찍어 serviceKey가 로그에 남는 문제 → 본문만 노출하도록 교체 완료

## 4. Supabase

**스키마**: `ingredients` `products` `daily_records` 생성 완료. `weather`/`skin`/`routine`은 jsonb(프롬프트 튜닝 시 마이그레이션 회피).

`product_ingredients`는 `raw_name` NOT NULL, `ingredient_id` nullable — OCR 매칭 실패해도 원문 보존.

`users` 테이블은 만들지 않았다. 익명 로그인이 `auth.users`에 행을 만들고, RLS가 `auth.uid()` 기준이라 불필요. 프로필 데이터가 생기면 그때 `profiles` 추가.

**RLS 격리 검증 16개 전부 통과.** 실제 방어선:

- B는 A의 제품을 조회·수정·삭제 불가
- B가 `user_id`를 A로 위조해 삽입 불가 (with check 절)
- B는 A의 셀카 기록 조회 불가
- B가 성분 사전에 쓰기 불가 (select만 열림)
- **B가 A의 셀카를 받지 못함 / 인증 없는 공개 URL로도 받지 못함 / 남의 폴더명으로 업로드 불가**

마지막 3개가 얼굴 사진 보호에 해당. 실측으로 검증됨.

**키**: 신규 체계(`sb_publishable_` / `sb_secret_`). secret 키는 RLS를 우회하므로 백엔드 `.env` 전용, 프론트·커밋 금지.
